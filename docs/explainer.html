1 · The idea in one paragraph

The chain is a public notary, not a database

The charity receives and spends money. People want to trust that the records we show them were not quietly edited later. So, every time money moves, we take a fingerprint of the record and post only that fingerprint to a public blockchain. The blockchain stamps it with a time and nobody, including us, can change or delete it afterwards. Later, anyone holding the record can fingerprint it again and compare. Same fingerprint means the record is exactly what it was when it was stamped.

The chain proves a record existed unchanged at a block time. It does not prove the record is true. If someone types a wrong amount before it is stamped, the chain will faithfully protect the wrong amount.

Think of a notary stamping a sealed envelope: the stamp proves when the envelope was sealed and that it has not been opened, but says nothing about whether the letter inside is honest.

2 · Blockchain basics

Eight words you need

BlockchainA shared, append-only list of transactions kept by thousands of computers. New entries are grouped into blocks; old blocks cannot be changed without everyone noticing.
Base SepoliaThe network we use. "Base" is a cheap Ethereum network; "Sepolia" means its test version: same technology, but the coins are free and worthless. Chain id 84532.
Smart contractA small program stored on the chain with its own storage. Ours is TransparencyLedger. Its rules (who may write, no overwrites) run on every node, so we cannot bypass them either.
Wallet / addressAn account on the chain, like 0xC16e…. Public, like an email address. Anyone can see what it did.
Private keyThe secret that lets a wallet sign. Whoever has it is that wallet. Ours live only in chain/.env, never in git or chat.
Transaction & gasA signed request to change chain state (e.g. "record this hash"). It costs a small fee called gas, paid in ETH. Reading the chain is free.
Block timeThe timestamp of the block that included our transaction. This is the "when" the chain can prove. Separate from the bank's own time.
RoleA permission inside our contract. RECORDER_ROLE may write records; the admin role may grant roles and pause the contract.
3 · Hashes and salt

The fingerprint: SHA-256 with a salt

A hash function turns any data into a fixed 32-byte value. Three properties matter: the same input always gives the same hash; changing even one character gives a completely different hash; and you cannot work backwards from the hash to the input.

But a hash alone has a weakness here. Donation records are guessable: an attacker could try "500,000 VND from D-001 on 16 Nov" and hash it, and if it matches what is on chain, they learned the record. So we add a salt: 16 random bytes generated per record and kept in our database. Without the salt, guessing is hopeless. With the salt, anyone we give it to can check.

Our exact formula, in transparency/merkle.py: leaf = SHA-256( 0x00 + salt + canonical JSON of the record ). "Canonical" means the keys are sorted and spacing is fixed, so the same record always produces the same bytes. The leading 0x00 marks it as a leaf so it can never be confused with an inner node of a Merkle tree (section 5).

4 · refId

The label on the envelope

The chain stores each fingerprint under a key so we can find it again. We cannot use the bank's transaction id directly, because that id is itself information. So the key is refId = HMAC-SHA256(REFID_SECRET, bank transaction id). HMAC is a hash mixed with a secret: only our server, which knows REFID_SECRET, can compute it, so outsiders cannot link a refId to a bank transfer.

The refId also stops duplicates. Bank webhooks often resend the same event. The contract refuses a second write for a refId it already has, and our Python bridge checks first and answers "exists" instead of paying for a failed transaction. If the same refId ever arrives with a different fingerprint, the bridge raises ConflictError: something changed a record that was already stamped, and a human must look.

Never change REFID_SECRET. If it changes, every future refId differs from the old ones, and we can no longer find old records on chain from their bank ids.

5 · Daily roots

Stamping a whole day at once

New transactions get stamped one by one. But the starting history (the Kaggle file Dong is cleaning) may have thousands of rows, and one transaction per row would cost a lot of gas. So for history we build a Merkle tree per day: hash the leaves in pairs, then hash those results in pairs, until one value is left, the root. Only the root goes on chain, with anchorBatch(day, root, count).

flowchart BT
  L1["leaf 1"] --> A["hash(1,2)"]
  L2["leaf 2"] --> A
  L3["leaf 3"] --> B["hash(3,4)"]
  L4["leaf 4"] --> B
  A --> R["ROOT of 16 Nov (on chain)"]
  B --> R

To prove leaf 3 belongs to that day, you need only leaf 3, its neighbour leaf 4, and hash(1,2): hash upward and see whether you land on the root. That list of neighbours is the proof; scripts/transparency.py prove produces it. Change any record of that day and the root no longer matches.

7 · The flows

Four journeys a record takes

A. A live donation arrives (built: transparency/listener.py, testnet, temporary record rules)

sequenceDiagram
  participant Bank as SePay webhook
  participant L as Listener
  participant DB as ledger_records
  participant B as chain.py
  participant C as Contract
  Bank->>L: transfer event (signed)
  L->>L: check signature, build record, new random salt
  L->>DB: save record + salt FIRST
  L-->>Bank: {"success": true} (SePay allows 30 s)
  L->>B: record(refId, leaf) from memory
  B->>C: entries(refId)? (free read)
  alt not on chain yet
    B->>C: record(refId, leaf) signed by listener key
    C-->>B: stored with block time
  else already there, same leaf
    B-->>L: "exists" (webhook retry, nothing sent)
  end
  L->>DB: save chain tx hash

The salt is saved before the chain write. If we lost the salt after stamping, the fingerprint on chain could never be checked again.

B. Loading the history (planned: waits for Dong's file)

  1. Read the cleaned file, one row per transaction, and build records with records.py.
  2. Group rows by day; give each a salt; compute leaves and the day's Merkle root.
  3. Save every record + salt + its day in ledger_records.
  4. Send one anchorBatch(day, root, count) per day.

C. Someone checks a record (built)

sequenceDiagram
  participant U as User
  participant V as POST /verify
  participant C as Contract
  U->>V: record + salt
  V->>V: rebuild leaf, compute refId
  V->>C: entries(refId)
  C-->>V: stored leaf + block time
  V-->>U: match true/false, block time

Three possible answers: match (unchanged since the block time), found but no match (the record or salt was altered), or not found (never stamped).

D. A staff member reads records (built)

  1. They call GET /api/ledger/records with their login token.
  2. The app looks up their department. Money in needs the label bank_transaction; money out needs disbursement. By default finance has both; admin and dev see everything; volunteer sees nothing until the admin changes the labels.
  3. Allowed: they get the records with salts, so they can verify them independently. Refused: 403, or 404 for a single record so ids cannot be probed. Both are written to the audit log.
  4. Optional ?check_chain=true re-checks that record against the chain on the spot.

9 · Decisions

What we chose and why

DecisionWhy
Hash everything on chain (client)A public chain is permanent: anything readable posted there can never be taken back, including donors' details. Readable data stays where access can be controlled and revoked.
Reuse the AI part's permissionsOne set of users, departments and labels for the whole system, managed by the admin, with one audit log. No second login system to secure.
Random salt per recordStops guessing attacks on predictable records. Lets us hand out proof for one record without exposing others.
refId = HMAC of the bank idHides bank ids, gives a stable key, lets the contract refuse duplicates.
Write-once, no update or deleteThe whole point. Corrections are new records that reference the old one, never edits.
One transaction per live record, one root per history dayLive records can be checked one by one immediately; history is cheap to stamp in bulk.
The listener is the only writer (RECORDER_ROLE)Limits who can stamp. If its key leaks, the admin pauses the contract and revokes the role. Two-person approval (multisig) is planned later.
Bank time kept apart from block timeBank time is what the bank says (inside the hashed record). Block time is what the chain proves.
Base Sepolia test networkFree, same technology as the real Base network. Moving to main network later is a redeploy, not a rewrite.
Public verify stays openIt only confirms data the caller already has, so it reveals nothing new.
10 · Limits

What the system cannot do

  • It cannot prove truth. We trust the listener to report what the bank said. A wrong record stamped is a wrong record protected.
  • It cannot prove completeness of live records. A record never stamped is simply absent. The bank's own statement is the cross-check.
  • It cannot bring data back. The chain holds fingerprints, not records. Lose the database or the salts and the proof is gone. Back them up.
  • The bank feed sends no names or recipient fields, and no balance (MB via SePay). Donors and recipients have to be identified by codes in the transfer memo.
  • The daily count is visible. Anyone can see how many history rows a day had. Pending client confirmation.
  • The v2 test entry is permanent. Harmless test data, but a reminder that nothing on chain can be deleted.

12 · Check yourself

Six questions

The chain says "match". Does that mean the donation really happened?

No. It means the record is unchanged since the block time. Whether the money really moved is checked against the bank statement.

Why can't we just hash the record without a salt?

Records are guessable. Someone could hash likely records and compare with the chain to learn amounts and donors. The random salt makes guessing impossible.

What happens if the webhook sends the same transfer twice?

Same bank id, so same refId. The bridge sees it is already on chain with the same leaf and returns "exists" without sending anything.

A volunteer asks for donor names. What do they get?

Nothing, by default: money-in records need the bank_transaction label, which only finance has. The refusal is logged. The admin can change labels.

We lose the database. Can we rebuild records from the chain?

No. The chain holds only fingerprints. That is why the database and salts must be backed up.

Why do history days use a Merkle root instead of one transaction per row?

Cost. One root per day covers any number of rows in one transaction, and each row can still be proven with a short list of neighbour hashes.
